**조사 할 때 신경쓰면 좋은 것**

- Python 파일을 처음 실행하면 코드가 어떤 순서로 실행되는가? (위에서 아래로? 함수의 정의와 실행 분리해서 생각하기 + 함수 정의 된건 언제 실행되나?)
- `print("A")` → `some_function()` → `print("B")` 순서로 작성하면 항상 A → 함수 내용 → B 순으로 출력되는가?
- 비동기로 처리될 때 코드의 실행 순서는 어떻게 달라지는가? `async`/`await`가 붙으면 Call Stack에서 무슨 일이 일어나는가?
- 콜백(Callback) 함수란 무엇이고, 왜 "나중에 불러줘"라는 패턴이 필요한가?
- JavaScript의 콜백 지옥(Callback Hell)이 Python에서는 어떻게 해결되었는가?

**제프 의견**

그리고 순서대로 실행하는것에 익숙졌다면 (코드가 한 줄씩 순차 실행되는 게 당연하다고 생각될 때) 비동기 환경에서는 어떻게 실행이 되는지 이해해야합니다.

- "A를 실행하고 → B를 기다리는 동안 → C를 먼저 처리하고 → B가 끝나면 다시 돌아온다"는 흐름을 명확하게 그림으로 그릴 수 있어야 합니다.

간단한 예제 코드를 만들고 실행 순서를 예측한 뒤 실제 결과와 비교해 보세요!

### 2. 비밀번호 보안과 해싱 (Password Security & Hashing)

**관련 주제 힌트:** bcrypt, passlib, 단방향 해시(One-way Hash), Salt, Rainbow Table Attack

**조사 할 때 신경쓰면 좋은 것**

- 왜 비밀번호를 데이터베이스에 그대로(평문으로) 저장하면 안 되는가?
- 해시(Hash)와 암호화(Encryption)의 차이는 무엇인가? 왜 비밀번호는 해시를 써야 하는가?
- Salt란 무엇이고, 왜 같은 비밀번호라도 다른 해시값이 나와야 하는가?
- bcrypt가 MD5나 SHA256보다 비밀번호 저장에 더 적합한 이유는? (키워드: 느린 해시)
- FastAPI에서 `passlib` 라이브러리를 사용해 비밀번호를 안전하게 저장하고 검증하는 방법은?

**제프 의견**

3주차에서 인증과 토큰을 설계했다면, 이번 주에는 **비밀번호를 어떻게 안전하게 저장하는지** 구현합니다.

"비밀번호 1234"를 그대로 DB에 저장했다가 해킹당하면? 모든 사용자의 비밀번호가 노출됩니다.

해시 함수로 비밀번호를 변환해서 저장하면 원래 비밀번호를 복원할 수 없어서 안전합니다.

bcrypt + Salt 조합을 직접 구현해 보고, 같은 비밀번호 "1234"가 매번 다른 해시값으로 저장되는 것을 확인해 보세요!

### 3. 요청/응답 모델링과 데이터 검증 심화 (Pydantic 실전)

**관련 주제 힌트:** BaseModel, Field Validation, Nested Model, Response Model, Request Body

**조사 할 때 신경쓰면 좋은 것**

- 클라이언트가 보낸 JSON 데이터가 FastAPI 함수 안으로 들어오기까지 어떤 과정을 거치는가?
- `response_model`을 지정하면 응답 데이터에서 특정 필드를 숨길 수 있는데.. 이건 어떻게 작동하는걸까? (예: 비밀번호 필드 제외)
- 중첩된 JSON 구조(예: 게시글 안에 작성자 정보)는 Pydantic으로 어떻게 표현하는가?
- `Field(min_length=1, max_length=100)` 같은 제약 조건은 내부적으로 어떻게 검사되는가?

**제프 의견**

Pydantic을 사용해봤다면 이번에는 **실전에서 어떻게 쓰는지**에 집중합니다.

회원가입 API를 만들 때 입력값 검증(이메일 형식, 비밀번호 길이 등)을 Pydantic으로 처리하고 응답할 때는 비밀번호를 빼고 보내는 패턴을 직접 구현하려면 어떻게 해야할까요?

이 패턴을 사용했을 때와 사용하지 않았을 때 각각 어떤 차이가 있는지 장점과 단점을 분석 후 발표해주세요

### 4. 에러 핸들링과 HTTP 상태 코드 (Exception Handling)

**관련 주제 힌트:** HTTPException, Custom Exception Handler, Status Code, Error Response Format

**조사 할 때 신경쓰면 좋은 것**

- FastAPI에서 404 Not Found 에러를 발생시키려면 어떻게 해야 하는가?
- `raise HTTPException(status_code=404)`와 `return JSONResponse(status_code=404)`의 차이는?
- 모든 API에서 동일한 에러 응답 포맷(예: `\{"status": "error", "message": "..."\}`)을 유지하려면 어떻게 해야 하는가?
- 예상치 못한 서버 에러(500)가 발생했을 때 클라이언트에게 민감한 정보가 노출되지 않게 하려면?

**제프 의견**

REST API 설계에서 에러 응답(400, 401, 403, 404, 409, 422, 500)을 정의했었지요

이제 그 설계를 실제 코드로 구현할 차례입니다.

에러 처리를 대충 하면 사용자는 "뭔가 안 됨"만 알게 될겁니다.
반대로 잘 해두면? "왜 안 되는지, 어떻게 고쳐야 하는지"까지 알려줄 수 있습니다.

### **핵심 미션**

**브라우저에 `aws13th.yimtaejong.com`을 입력하고 엔터를 딱 쳤을 때, 무슨 일이 벌어질까요?**

**활용할 수 있는 도구 목록**

- **DNS 조회:** `nslookup`, `dig`, `host`, `drill`
- **도메인 정보:** `whois`, 온라인 WHOIS 서비스
- **네트워크 경로 추적:** `traceroute`, `tracert`, `mtr`, `pathping`
- **연결 테스트:** `ping`, `telnet`, `nc(netcat)`
- **HTTP 통신 확인:** `curl`, `wget`, `httpie`
- **브라우저 도구:** 개발자 도구(F12) Network 탭, Lighthouse
- **패킷 분석:** `tcpdump`, Wireshark
- **포트 스캔:** `netstat`, `ss`, `lsof`

**조사 할 때 신경쓰면 좋은 것**

- **1단계 (DNS 조회):** 브라우저가 `aws13th.yimtaejong.com`을 IP 주소로 바꾸는 과정은? → `nslookup`으로 직접 확인
- **2단계 (TCP 연결):** IP를 알아냈으면 어떻게 연결을 수립하는가? (3-way handshake) → `curl -v`로 확인
- **3단계 (HTTP 요청):** 연결 후 어떤 데이터를 주고받는가? → 개발자 도구 Network 탭으로 확인
- **4단계 (렌더링):** 받은 HTML/CSS/JS를 브라우저가 어떻게 화면으로 그리는가?
- **추가 질문:** `traceroute` 결과에서 패킷이 몇 개의 라우터를 거쳐 가는가? 각 라우터는 어느 회사(통신사) 소속인가?

**제프 의견**

배포를 배우기 전에 **반드시 알아야 할 기초 지식**입니다.

"서버에 배포했는데 접속이 안 돼요" ← 이런 문제의 대부분은 DNS, 포트, 방화벽 문제에요

책이나 블로그에서 이론만 읽으면 절대 외워지지 않습니다.

**직접 도구를 돌려보고 그 결과를 설명할 수 있어야** 진짜 이해한 겁니다.

발표 때 터미널 실행 결과 스크린샷을 꼭 포함하세요!!!

## 3. 환경 변수와 설정관리
1. 환경 변수 (Environment Variables)란?
환경 변수는 운영체제(OS) 레벨에서 관리되는 키-값(Key-Value) 쌍의 변수입니다. 프로그램 외부에서 값을 설정하기 때문에,
소스 코드를 수정하거나 다시 빌드하지 않고도 프로그램의 동작을 바꿀 수 있습니다.

2. 설정 관리 (Configuration)가 필요한 이유?
개발을 하다 보면 코드는 같지만, 환경에 따라 달라져야 하는 정보들이 있습니다. 이를 위해 환경 변수를 사용해 서버(접속 대상)를 변경하는 것이 
현대 인프라 관리의 핵심이며, 상황에 따라 '코드 수정 없이' 접속 대상을 갈아끼우는 것이다.


## 4. 환경변수를 왜 쓰나?

1. 보안 (Security): 민감한 정보 보호
가장 중요한 이유입니다. 데이터베이스 비밀번호, 결제 API 키, 암호화 토큰 등을 회원의 인증과 권한을 제어하는데 
핵심적으로 쓰이는 값으로 이를 실제 비즈니스 로직 코드에 적어두어(하드코딩 방식), 코드가 공유되는 순간 보안 사고가 발생합니다. 

해당 값은 민감한 개인정보를 포함하고 있으며 철저한 관리가 필요하다. 더욱이 웹상에는 키값으로 신원 인증 및 결제가 실제로 이루어 지는
서비스가 많으므로, 키 값은 절대 외부 유출에 유의 해야한다. 그러므로 해당 키 값은 감추고 이를 변수화 하여 운영체제 단위에 저장해두고
실제 프로그램 코드상에는 변수만 호출하여 키를 외부에 유출하지 않고, 키값을 조작할수 있다.

2. 유연성 및 이식성 (Portability): 코드 한 번으로 어디서나 실행

프로그램은 개발자의 컴퓨터(Local), 테스트 서버(Staging), 실제 서비스 서버(Production) 등 다양한 곳에서 돌아갑니다. 
각 장소마다 환경 설정이 다른데, 환경 변수를 쓰지 않으면 매번 코드를 수정해야 합니다.

환경별 차이:

로컬: DB_HOST = localhost

운영 서버: DB_HOST = 10.0.x.x (실제 DB 주소)

해결: 코드는 process.env.DB_HOST처럼 변수 이름만 참조하게 짜고, 실제 값은 각 서버 환경에 맞게 따로 설정합니다. 
이를 통해 **"빌드는 한 번만, 배포는 어디든(Build Once, Run Anywhere)"**이 가능해집니다.


3. 관리 효율성 (Efficiency): 설정 변경의 용이성
시스템의 동작 방식을 바꿀 때마다 코드를 수정하고 다시 컴파일(또는 빌드)하여 배포하는 과정은 매우 번거롭고 위험합니다.

상황: 갑자기 서버 포트를 3000번에서 8080번으로 바꿔야 할 때.

해결: 환경 변수 값만 PORT=8080으로 수정하고 프로그램을 재시작하면 됩니다. 코드 수정이 없으므로 실수로 다른 로직을 건드릴 위험이 사라집니다.


4. 모든 프로그램이 공통적으로 참조해야 하는 설정값

운영 체제의 위치 통일, 다른 프로그램(도구)들과의 협업 만약 JAVA_HOME이 없다면, 자바를 사용하는 모든 프로그램(이클립스, 인텔리제이, 톰캣 등)은 실행될 때마다 사용자에게 "자바 설치 폴더가 어디인가요?"라고 물어봐야 합니다. 하지만 JAVA_HOME을 설정해두면, 

프로그램들은 군말 없이 "JAVA_HOME 변수에 적힌 폴더로 가면 자바가 있겠군!" 하고 바로 찾아갑니다.

또한 우리가 명령 프롬프트(CMD)에서 python이나 node, git이라고 쳤을 때 프로그램이 바로 실행되는 이유가 바로 Windows 환경 변수의 Path에 그 프로그램들이 설치된 경로가 등록되어 있기 때문입니다.

이유: OS에게 "누가 어디서든 이 이름을 부르면 이 폴더에 있는 파일을 실행해줘"라고 전역적인 명령을 내리는 것입니다.

비유: 도시 전체(OS)에 "어디서든 '경찰서'라고 외치면 가장 가까운 경찰서 위치를 알려줘"라고 공지하는 것과 같습니다.


## 5. 환경변수 종류별 사용 방법
환경변수를 다루는 방법은 여러게가 있으며 각각의 특징이 있다.

1. 직접방식 : 운영체제에 직접 환경변수를 심는 방식 

1-1 내가 직접 쓰고 있는 내 컴퓨터 OS에 심기
- windows의 '환경변수' 설정으로 운영체제 안에 변수를 심는 과정으로
- 프로그램의 설정값을 통일 시켜 운영체제에서 쓸수 있게 하거나(Python 변수 등록으로 여러 운영 체제에서 파이썬을 쓸수 있음),
- 프로그램을 참조하는 여러 하위 프로그램들에게 변수를 지정해 주어 위치를 찾아갈수 있게 해준다(JAVA_HOME을 등록하면 이클립스에서 자바의 디렉토리 값을 바로 알고 쓸수 있다.
- cmd 프로그램에서 node같은 path 환경 변수로 node.js디렉토리 값을 읽어 node명령어를 쓸수 있게 해준다.)
- Linux/macOS의 .bashrc나 .zshrc 파일. 등으로 운영체제에 자신의 변수와 값을 지정에 놓으면, 터미널 세션을 껐다켜도 자신만의 
터미널 값을 변수로 쓸수 있다.
- 테스트 및 한번 쓰고 버리는 상수 변수로 운영체제 환경변수를 사용 NODE_ENV=production npm start 같은건 cmd에 상수로 한번만 존재하는
변수로 터미널 종료시 바로 삭제됨

1-2 프로그램을 실행하기 위해 만든 가상 OS (Docker)
- 도커 사용시, 도커 환경은 운영체제 안에 존재하는 리눅스배경 가상환경으로 docker run -e DB_HOST=production_db my_app 같이 도커 컨테이너 가상환경에서 돌아가는 변수 지정,내 컴퓨터 OS는 깨끗하게 유지하면서, 
프로그램이 돌아가는 가상 OS 환경에만 변수를 심을 수 있습니다. 서버 배포의 표준이 된 방식입니다
-서버에서 프로그램이 24시간 돌아가게 하려면 리눅스의 systemd라는 서비스로 등록합니다.서비스 설정 파일(.service) 안에 Environment="VOTE_DB_URL=postgres://..." 식으로 작성합니다.
컴퓨터가 재부팅되어도 OS가 서비스를 다시 시작할 때 이 변수들을 자동으로 다시 심어줍니다. 사람이 개입하지 않아도 서버가 항상 올바른 설정값으로 작동하게 보장합니다

1-3 배포를 도와주는 원격지의 임시 OS (CI/CD)
- GitHub Actions로 배포시 서버를 지정 : GitHub Actions은 GitHub에서 제공해주는
클라우드 러너(리눅스 환경 클라우드 제공)로 간접방식에 사용하는 YAML 상단에 서버 변수를 지정하여 배포시 일괄 변환 해준다.
- GitHub Environment에 서버 변수를 저장하거나, GitHub Secret으로 키값을 전부 생성하여 GitHub Actions로 배포시 임시로 
.env파일을 생성하여 값을 주입후 터미널 세션 종료시 값을 삭제한다.

Jenkins 같은 서비스는 코드를 클라우드 환경에 올리고 빌드하고 배포하기 위해 위와같이 간접, 직접방식으로 변수값을 지정하여 서버 변경 배포 가능

2. 간접방식 : 운영체제가 아닌 다른 곳에 환경변수를 만들어 놓고, 실행시점에 필요한 변수만 호출하는 방식 

2-1 .env 방식(Environment File) : 키:값으로 이루어진 간단한 텍스트 파일로, 값을 바로 키로 변수 지정이 가능하며,
한번 지정하면 변하지 않는 상수 값들을 지정할때 주로 사용, '.' 도트파일은 리눅스 환경 생테계에서 설정상 민감하여 숨김처리 
하는 파일이며, 이는 개발자의 암묵적 규칙으로 비즈니스 로직을 담지않는 민감한 정보를 담는 운영체제 시스템 파일을 의미한다.

2-2 YAML(Yet Another Markup Language)방식
변수들의 복잡한 동작 방식을 체계적으로 구조화 할때 쓰는 텍스트 기반 파일(타입 변경, 주석처리가능,파이썬 처럼 들여쓰기로 계층구조화 관리 가능)
쉽게 변하는 변수명이거나 변수들이 여러 계층구조를 가질때 사용한다.


그럼 AWS ec2는 어떤 방식이냐?

직접과 간접을 모두 사용
직접 조작시 ec2를 처음 생성할때(부팅)할때 쓰는 스크립트에 변수를 지정할수 있다.
ec2 인스턴스 안에 .bashrc를 생성하여 변수를 심을수 있다.
ec2안에 .env파일을 만들어서 실행시 변수값을 불러오게 할수 있다.

## 6. 환경변수 실제 사례
1. DATABASE_URL = "localhost:5432"로 코드를 짜고 배포하면 왜 AWS에서 베포가 안될까?

localhost는 운영체제 시스템에 hosts라는 파일에 정의 되어있는 이름중 하나로 변수는 아니다.
개인의 로컬 os는 localhost를 미리 정의 해놓은 파일이 있기 떄문에 localhost:5432 로 값을 지정하고 .env로 
로컬의 환경에서 돌릴시는 잘돌아간다.

하지만 배포시 AWS는 본인의 운영체제가 아닌 클라우드의 운영체제로 AWS 운영체제도 localhost라는 값이 정의 되어 있는 파일이 있지만
자신의 배포 코드와 DB를 직접 심는 경우는 없기 때문에 localhost로는 주소를 찾을수 없다. (만약 ec2내부에 db까지 전부 심으면 localhost로 조작도 가능하지만
이경우는 외부에서 localhost가 가르키는 주소가 달라서 배포가 불가하다.)

배포를 위해서 배포할때만 localhost를 aws-db-address.com로 바꿔서 사용한다고 가정하면, 배포시 매번 수정해야하며
내 코드를 다시 로컬 환경에서 개발하기 위해서는 localhost로 다시 바꿔야 한다. 또한 git같은 버전 관리 프로그램을 이용한다면 
DB에대한 입력값이 매번 달라지기 때문에 불필요한 커밋 기록이 쌓일수 밖에 없게된다.

이를 위해 aws의 환경과, 나의 로컬 환경을 이어주는 환경 변수를 지정해야한다.
코드상에서는 DATABASE_URL = process.env.DB_URL로 db가 가야할 절대 경로를 적어주고
.env 파일에는 DB_URL=localhost, asw서버에는 DB_URL=aws-db-address.com로 등록하면
로컬에서 db가 돌아가는 상황과, aws의 배포의 상황이 자동으로 핸들링 된다.

2. .env 파일이란 무엇이고, python-dotenv로 어떻게 불러오는가? 실제로 .env의 값이 python코드로 어떻게 들어오는가?
.env는 환경 변수들을 모아놓은 단순한 텍스트 파일입니다. 파일 이름 자체가 .env이며, 프로젝트의 최상위 루트 폴더에 둡니다.
파이썬 프로그램은 기본적으로 .env 파일의 존재를 모릅니다. 그래서 python-dotenv라는 라이브러리가 "파일을 읽어서 운영체제의 메모리(환경 변수 공간)로 옮겨주는" 역할을 합니다.

이 과정은 단순히 파일을 읽는 것을 넘어, 운영체제의 개입이 일어납니다.

load_dotenv() 실행: * 라이브러리가 현재 폴더의 .env 파일을 엽니다.

한 줄씩 읽으면서 DB_URL이라는 이름과 localhost라는 값을 분리합니다.

OS 메모리 주입 (직접 방식의 자동화):

파이썬은 운영체제에게 명령합니다: "이 변수들을 현재 실행 중인 내 프로세스의 환경 변수 목록(os.environ)에 등록해줘!"

이제 이 변수들은 파일이 아니라 운영체제의 메모리에 박히게 됩니다.

os.getenv() 호출:

코드가 실행될 때 파일로 다시 가보는 것이 아니라, 이미 메모리에 올라와 있는(OS가 관리하는) 환경 변수 중에서 해당 이름을 찾아 그 값을 가져옵니다.


3. FastAPI에서 pydantic-settings를 사용해 환경 변수를 타입 안전하게 관리하는 방법은?

환경 변수를 관리할 때 os.getenv를 사용하면 모든 값이 **문자열(String)**로 들어옵니다. 예를 들어 .env에 PORT=8000이라고 적어도 파이썬은 이를 숫자 8000이 아닌 문자 "8000"으로 읽죠.

pydantic-settings는 이 문자열을 우리가 원하는 타입(int, bool, list 등)으로 **자동 변환(Validation)**하고, 
필수 변수가 누락되면 서버 실행을 막아주는 아주 강력한 도구입니다.

```
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    # 변수명과 타입을 정의 (타입 안전성 확보)
    APP_NAME: str
    ADMIN_EMAIL: str
    DATABASE_URL: str
    ITEMS_PER_PAGE: int = 10  # 기본값 설정 가능
    DEBUG: bool = False       # "True", "true", "1" 모두 True로 자동 변환됨

    # .env 파일을 읽어오기 위한 설정
    model_config = SettingsConfigDict(env_file=".env")

# 인스턴스 생성
settings = Settings()

```
왜 pydantic-settings를 쓰는가? (강점)
자동 타입 변환 (Type Casting): .env의 "20"을 int로, "True"를 bool로 알아서 바꿔줍니다.

데이터 검증 (Validation): 만약 ADMIN_EMAIL에 이메일 형식이 아닌 값이 들어오면 서버 실행 단계에서 즉시 에러를 발생시켜 잘못된 설정으로 서버가 돌아가는 것을 방지합니다.
우선순위 관리: pydantic-settings는 다음 순서로 값을 찾습니다.
1순위: 운영체제(OS)에 직접 심긴 환경 변수 (배포 환경)
2순위: .env 파일 (로컬 개발 환경)
이 덕분에 코드를 수정하지 않고도 로컬과 배포 환경(AWS)을 넘나들 수 있습니다.

4. 서버에서 환경 변수는 어디에 설정하는가? (EC2 인스턴스, Docker, 클라우드 서비스 등)

서버 환경에서 환경 변수를 설정하는 곳은 **"내 프로그램이 어떤 옷(환경)을 입고 실행되느냐"**에 따라 달라집니다.

4-1. AWS EC2 (가상 서버 OS에 직접 설정)

EC2는 일반적인 리눅스 컴퓨터와 같습니다. 운영체제 레벨에서 환경 변수를 심는 방식입니다.

* **임시 설정:** 터미널에서 `export DB_URL=localhost` 입력 (로그아웃 시 사라짐).
* **영구 설정:** 사용자의 홈 디렉토리에 있는 `.bashrc` 또는 `.profile` 파일에 `export` 구문 추가.
* **시스템 서비스 설정:** 앞서 배운 `systemd` 서비스 파일(`.service`) 내부에 `Environment="KEY=VALUE"` 작성. (가장 권장되는 서버 운영 방식)

4-2. Docker (컨테이너 실행 시 주입)

도커는 이미지를 빌드할 때나 컨테이너를 실행할 때 변수를 꽂아 넣습니다.

* **Dockerfile:** 이미지 생성 단계에서 고정할 값 설정.
```dockerfile
ENV APP_HOME=/app

```

* **Docker Run 명령:** 실행 시점에 동적으로 주입.
```bash
docker run -e DB_URL=prod-db.com my-app

```

* **Docker Compose:** `docker-compose.yml` 파일의 `environment:` 항목에 작성하거나 `.env` 파일을 참조하게 설정.

---

4-3. 클라우드 서비스 (PaaS / Serverless)

AWS Lambda, Vercel, Heroku 같은 서비스들은 OS에 접속할 수 없으므로, **웹 콘솔(GUI)**에서 변수를 입력합니다.

* **AWS Lambda:** AWS 콘솔의 '구성(Configuration) > 환경 변수' 메뉴에서 입력.
* **Vercel / Netlify:** 프로젝트 설정(Settings)의 'Environment Variables' 메뉴에 키와 값을 입력.
* **AWS ECS / Kubernetes:** 컨테이너 정의 파일(Task Definition)이나 `ConfigMap`, `Secret` 설정을 통해 주입.

---

4-4. 환경별 설정 위치 요약 표

| 환경 | 주요 설정 위치 | 특징 |
| --- | --- | --- |
| **로컬 개발** | `.env` 파일 | 개발 편의성, `gitignore` 필수 |
| **AWS EC2** | `/etc/systemd/system/*.service` | OS 서비스 관리자가 프로그램 실행 시 주입 |
| **Docker** | `docker-compose.yml` 또는 `ENV` | 컨테이너 독립성을 유지하며 환경 제어 |
| **클라우드(PaaS)** | 서비스 제공사 웹 콘솔 (Settings) | 인프라 관리자가 웹에서 안전하게 관리 |
| **CI/CD (GitHub)** | `Settings > Secrets` | 배포 과정에서 필요한 비밀 키 관리 |

--

> "배포 환경에서는 **절대로 `.env` 파일을 서버에 직접 올리지 마세요.** 대신 서버의 **시스템 설정(Systemd)**이나 **클라우드 콘솔(Secrets)**을 통해 변수를 **직접 주입**하는 것이 보안과 자동화 측면에서 훨씬 유리합니다."

이제 환경 변수가 어디에 위치해야 하는지 전체적인 지도가 완성되었습니다!

혹시 이 중에서 **"실제로 내 프로젝트를 EC2에 올릴 때, 어떤 방식을 선택하는 게 가장 좋을지"** 구체적인 가이드가 필요하신가요? 아니면 다른 궁금한 점이 있으신가요?

5. YAML 파일의 사용
Docker Compose (docker-compose.yml): 여러 개의 컨테이너를 한꺼번에 띄울 때 어떤 이미지를 쓰고, 어떤 포트를 열지 정의합니다.

GitHub Actions (.github/workflows/*.yml): 배포 순서와 조건을 정의하는 배포 시나리오를 작성할 때 씁니다.

Kubernetes (K8s): 클라우드 상의 수많은 컨테이너들이 어떻게 통신하고 배치될지 설계도로 씁니다.

Spring Boot (application.yml): 자바 기반 서버 프로그램의 세부 설정을 관리할 때 씁니다.

## 7. 설정관리

설정 관리란 : 환경 변수를 사용해 서버(접속 대상)를 변경하는 것은,현대 인프라 관리의 핵심입니다. 
상황에 따라 '코드 수정 없이' 접속 대상을 갈아끼우는 4가지 대표적인 실무 예시를 정리해 드립니다.

1. 개발(Local) vs 운영(Production) DB 전환
가장 고전적이고 필수적인 예시입니다. 개발자의 컴퓨터와 실제 서비스 서버가 바라보는 DB 주소를 분리합니다.

코드: db_host = os.getenv("DB_HOST")

환경별 설정:

로컬 (.env): DB_HOST=localhost (내 컴퓨터 DB)

운영 (EC2/RDS): DB_HOST=prod-db.aws.com (실제 고객 데이터 DB)

효과: 개발자가 실수로 운영 DB를 삭제하는 대참사를 방지합니다.

2. API 엔드포인트 전환 (외부 서비스)
결제 모듈(Toss, KakaoPay)이나 메일 전송 서비스(SendGrid) 등을 사용할 때 '테스트용'과 '실제용' 서버 주소를 나눕니다.

코드: api_url = os.getenv("PAYMENT_API_URL")

환경별 설정:

테스트 환경: PAYMENT_API_URL=https://sandbox-api.test.com (가짜 결제)

운영 환경: PAYMENT_API_URL=https://api.real-service.com (실제 돈 결제)

효과: 실제 결제 없이도 안전하게 기능을 테스트할 수 있습니다.

3. 프론트엔드 배포 환경 전환 (Vercel/Netlify)
React나 Next.js 앱이 데이터를 요청할 백엔드 서버 주소를 결정할 때 사용합니다.

코드: const API_BASE = process.env.REACT_APP_API_URL;

환경별 설정:

스테이징(Staging): REACT_APP_API_URL=https://dev-api.mysite.com (팀원 확인용)

프로덕션(Production): REACT_APP_API_URL=https://api.mysite.com (사용자용)

효과: 동일한 빌드 결과물이 어느 서버로 요청을 보낼지 자유롭게 결정합니다.

4. 마이크로서비스(MSA) 간의 통신 주소
여러 개의 작은 서비스들이 서로를 호출할 때, 서비스의 위치가 바뀌어도 코드 수정을 하지 않기 위해 사용합니다.

상황: '주문 서비스'가 '재고 서비스'를 호출해야 함.

환경별 설정:

Docker Compose: STOCK_SERVICE_URL=http://stock-container:8080 (컨테이너 이름으로 통신)

Kubernetes: STOCK_SERVICE_URL=http://stock-service.default.svc.cluster.local (내부 DNS 사용)

효과: 인프라 환경이 도커에서 쿠버네티스로 이사를 가도 프로그램은 영향을 받지 않습니다.

5. 배포 자동화(CI/CD) 시 접속 타겟 전환
GitHub Actions에서 빌드된 결과물을 어느 서버에 올릴지 결정할 때 사용합니다.

YAML 예시: host: ${{ secrets.DEPLOY_TARGET_IP }}

상황별 설정:

Main 브랜치 푸시: DEPLOY_TARGET_IP에 운영 서버 IP 주입

Develop 브랜치 푸시: DEPLOY_TARGET_IP에 테스트 서버 IP 주입

효과: 브랜치에 따라 배포되는 '서버'를 자동으로 물리적으로 분리합니다.

💡 최종 요약: 서버 변경을 위한 '전략'
환경 변수를 통한 서버 변경은 결국 **"변수명(Key)은 '목적'을 나타내고, 값(Value)은 '위치'를 나타낸다"**는 원리를 따릅니다.

Key: DB_URL (나는 DB에 가고 싶어)

Value: localhost 또는 1.2.3.4 (지금은 여기가 주소야)



회원가입 비밀번호 로직
회원가입 요청부터 비밀번호 해싱, JWT 발급, 그리고 안전한 응답까지의 전체 과정을 흐름도로 정리해 드립니다.

이 그림은 데이터가 서버 내부에서 어떻게 변하고, 어떤 정보가 외부로 나가는지를 보여줍니다.

🛡️ 안전한 회원가입 및 JWT 발급 시퀀스

1. 흐름 상세 설명
Step 1: 클라이언트 요청 (Request)
유저가 email, password, username, avatar를 담아 Multipart Form 형태로 전송합니다.

이때 비밀번호는 아직 평문(1234) 상태입니다.

Step 2: Pydantic & Validator 검증
FastAPI가 데이터를 받기 전, 우리가 정의한 Annotated와 Validator가 작동합니다.

비밀번호가 8자 이상인지, 이미지가 올바른 형식인지 검사하고 통과하지 못하면 여기서 바로 422 에러를 보냅니다.

Step 3: 비밀번호 해싱 (Hashing)
검증이 끝난 직후, 서버 내부에서 passlib(bcrypt)를 사용해 비밀번호를 **해시값($2b$12$...)**으로 변환합니다.

중요: 이 시점 이후로 서버 메모리에서 평문 비밀번호는 즉시 삭제되어야 합니다.

Step 4: 데이터베이스 저장 (DB Save)
DB에는 email, username, 그리고 해시된 비밀번호만 저장합니다.

유저가 보낸 이미지는 스토리지(S3 등)에 저장하고 그 URL만 DB에 기록합니다.

Step 5: JWT 토큰 생성
가입 성공 직후, 유저 ID를 담은 Access Token을 생성합니다.

Step 6: 안전한 응답 (Response)
클라이언트에게 SignupResponse 규격에 맞춰 데이터를 보냅니다.

포함 데이터: access_token, user_id, email, nickname, profile_image_url.

제외 데이터: 비밀번호(평문 및 해시값 모두 제외).

2. 왜 이 로직이 완벽한가요?
보안성: 서버가 털려도 DB에는 해시값만 있으므로 실제 비밀번호 유출을 막습니다.

무결성: Pydantic이 잘못된 데이터 입력을 입구에서 차단합니다.

로직 구조 회원가입과, 로그인 과정 2개 모두 토큰을 '생성' 한다.

결론적으로 말씀드리면, 회원가입(Signup)과 로그인(Login) 양쪽에서 토큰을 생성하여 반환하는 것은 아주 적절한 설계입니다.

그 이유는 다음과 같습니다.

1. 사용자 경험(UX) 측면
Signup 시 토큰 발급: 사용자가 회원가입 버튼을 누르자마자 서비스 메인 화면으로 진입할 수 있게 해줍니다. 만약 여기서 토큰을 주지 않으면, 사용자는 가입하자마자 다시 로그인 페이지로 가서 방금 만든 아이디를 또 입력해야 하는 번거로움이 생깁니다.

Login 시 토큰 발급: 이미 가입한 사용자가 나중에 다시 접속했을 때 출입증을 받는 정석적인 과정입니다.

2. 로직의 일관성
두 엔드포인트 모두 응답 모델로 **UserResponse**를 사용하고 계시죠?

UserResponse 모델이 access_token 필드를 필수로 가지고 있다면, 회원가입 성공 시에도 해당 모델 형식을 맞춰주어야 하기 때문에 토큰을 생성해서 넘겨주는 것이 로직상 자연스럽습니다.

3. 흐름 요약
Signup: [정보 입력] → [DB 저장] → [즉시 토큰 발급] → [로그인 상태로 진입]

Login: [ID/PW 입력] → [DB 대조] → [토큰 발급] → [로그인 상태로 진입]

결국 **"어떤 경로를 통하든 최종 목적지는 '로그인 된 상태'가 되는 것"**이므로, 두 함수 모두 create_access_token을 호출하는 것은 매우 합리적인 선택입니다.


race condition이란?
1. 경쟁 조건 (Race Condition)이란?
여러 개의 프로세스나 스레드가 동시에 동일한 데이터에 접근하여 조작하려고 할 때, 실행 순서에 따라 결과가 달라지는 상황을 말합니다.

회원가입에서의 예시 (찰나의 순간):

유저 A와 B가 거의 동시에 같은 이메일(test@test.com)로 가입 버튼을 누릅니다.

스레드 1 (유저 A 담당): DB에 "이 이메일 있어?" 물어봅니다. -> DB: "아니, 없어!"

스레드 2 (유저 B 담당): (거의 동시에) DB에 "이 이메일 있어?" 물어봅니다. -> DB: "아니, 없어!" (아직 유저 A의 데이터가 INSERT 되기 전이라서)

스레드 1: "그럼 가입시켜야지" 하고 INSERT 성공.

스레드 2: "나도 아까 없다고 들었어" 하고 INSERT 성공.

결과: DB에 동일한 이메일을 가진 유저가 2명 생겨버립니다. (데이터 무결성 파괴)

2. DB에 UNIQUE 제약 조건을 만드는 이유
코드(Python)에서 if cursor.fetchone():으로 체크하는 것은 "안내문" 같은 역할이라면, DB의 UNIQUE 제약 조건은 "강력한 자물쇠" 역할을 합니다.

① 최후의 보루 (데이터 무결성 보장)
애플리케이션 서버가 아무리 빨라도 위에서 설명한 찰나의 시간 차를 완벽히 막기는 어렵습니다. 하지만 DB 엔진 레벨에서 UNIQUE가 걸려 있으면, DB는 INSERT 직전에 인덱스를 확인하여 **원자성(Atomicity)**을 보장하며 중복 입력을 막아버립니다. 나중에 들어온 요청은 IntegrityError를 내며 실패하게 됩니다.

② 성능 향상 (인덱싱)
UNIQUE 제약 조건을 걸면 DB는 해당 필드에 대해 **인덱스(Index)**를 자동으로 생성합니다.

중복 체크를 위해 SELECT * FROM users WHERE email = ...을 실행할 때, 전체 테이블을 뒤지는(Full Scan) 게 아니라 인덱스를 통해 빛의 속도로 찾아냅니다.

③ 서비스 신뢰도
이메일이나 ID는 시스템에서 사용자를 식별하는 고유 키입니다. 중복 데이터가 들어가는 순간, 이후 로그인 로직에서 "결과가 2개 이상입니다"라는 에러가 터지거나, 엉뚱한 사람의 계정으로 로그인되는 대형 보안 사고가 날 수 있습니다.

3. 결론: 어떻게 구현해야 할까?
가장 좋은 방법은 두 가지를 모두 사용하는 것입니다.

코드에서 체크: 유저에게 "이미 사용 중인 이메일입니다"라고 친절한 에러 메시지를 빨리 보내주기 위해 필요합니다.
코드레벨에서 체크하는것은 코드(Python)에서 if cursor.fetchone():으로 체크하는 것은 "안내문" 같은 역할이라면, DB의 UNIQUE 제약 조건은 "강력한 자물쇠" 역할을 합니다.

DB UNIQUE 제약: 경쟁 조건으로 인해 코드를 통과한 중복 요청이 DB를 망가뜨리지 않도록 최종적으로 차단합니다.

추천하는 MariaDB 테이블 설정:

SQL
ALTER TABLE users ADD CONSTRAINT UNIQUE (email);
이렇게 하면 동시에 100명이 같은 이메일로 가입을 시도해도, DB 엔진이 단 한 명만 성공시키고 나머지는 모두 에러를 뱉어내어 시스템을 안전하게 지켜줍니다.

매번 서비스 로직에 get_db_connection()를 쓰는것은 매번 db연결을 시도하며, 부하를 주기때문에 비효율적 커넥션 풀(Connection Pool)을 도입
커넥션 풀(Connection Pool) 도입은 **상용 서비스로 나아가기 위한 필수적인 단계**입니다. 아주 좋은 지적을 받으셨네요!

왜 커넥션 풀이 필요한지, 그리고 FastAPI에서 어떻게 구현하는지 핵심만 짚어드릴게요.

---

### 1. 왜 커넥션 풀을 써야 하나요?

매번 `get_db_connection()`을 호출해 새로운 연결을 만드는 것은 마치 **심부름을 시킬 때마다 매번 새로 사람을 고용하고 해고하는 것**과 같습니다.

* **비용 절감:** DB 연결을 맺는 과정(TCP 핸드셰이크, 인증 등)은 CPU와 시간을 많이 소모합니다. 풀을 쓰면 미리 연결을 맺어두고 **재사용**하므로 응답 속도가 비약적으로 빨라집니다.
* **자원 관리:** 무한정 연결이 생성되는 것을 막아 DB 서버가 과부하로 뻗는 것을 방지합니다.

---

### 2. FastAPI에서 구현 방법 (SQLAlchemy 활용)

FastAPI에서는 직접 `PyMySQL`로 풀을 관리하기보다는, 데이터베이스 툴킷인 **SQLAlchemy**의 기능을 빌려 커넥션 풀을 관리하는 것이 표준입니다. (내부적으로 PyMySQL을 엔진으로 쓸 수 있습니다.)

#### Step 1: DB 설정 (database.py)

`pool_size`와 `max_overflow` 설정을 통해 풀을 제어합니다.

```python
from sqlalchemy import create_all_engines, create_engine
from sqlalchemy.orm import sessionmaker

# PyMySQL 엔진을 사용하되 풀링 기능 활성화
DATABASE_URL = "mysql+pymysql://user:password@localhost/dbname"

engine = create_engine(
    DATABASE_URL,
    pool_size=10,        # 항상 유지할 연결 개수
    max_overflow=20,     # 급증 시 추가로 허용할 연결 개수
    pool_recycle=3600,   # 1시간마다 연결 재휘발 (MariaDB 타임아웃 방지)
    pool_pre_ping=True   # 연결이 살아있는지 확인 후 빌려줌
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

# Dependency로 사용할 함수
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close() # 실제 종료가 아니라 풀로 반납됨

```

#### Step 2: 라우터에서 사용 (users.py)

이제 `get_db_connection()`을 직접 호출하는 대신 FastAPI의 `Depends`를 활용합니다.

```python

    db: Session = Depends(get_db) # 커넥션 풀에서 연결을 하나 빌려옴
):

    # SQLAlchemy의 ORM을 쓰거나, db.execute()로 생 SQL 실행 가능
    ...

```

### 3. 만약 SQLAlchemy 없이 PyMySQL만 쓰고 싶다면?

SQLAlchemy 도입이 부담스럽다면 `PyMySQL` 전용 풀 라이브러리인 `DBUtils`를 사용할 수도 있습니다.

```python
from dbutils.pooled_db import PooledDB
import pymysql

# 풀 생성 (앱 시작 시 한 번만 실행)
pool = PooledDB(
    creator=pymysql,
    maxconnections=10,
    host='localhost',
    user='root',
    password='password',
    database='my_db',
    cursorclass=pymysql.cursors.DictCursor
)

def get_db_connection():
    return pool.connection() # 새로 만드는 게 아니라 풀에서 꺼내옴

```

### 💡 정리 및 제안

1. **성능:** 유저가 10명만 넘어가도 커넥션 풀을 쓰는 쪽이 훨씬 안정적입니다.
2. **추천:** 가급적 **SQLAlchemy**를 도입해 보세요. 단순히 풀링뿐만 아니라 나중에 데이터 모델이 복잡해질 때 관리하기가 훨씬 편해집니다.

네, 정확한 지적입니다! **FastAPI의 LifeSpan(또는 Startup) 이벤트**에서 풀을 초기화하고, **Dependency Injection(DI)**으로 주입하는 패턴은 FastAPI 개발 시 가장 권장되는 **표준 아키텍처**입니다.

이렇게 하면 앱이 켜질 때 딱 한 번 풀이 생성되고, 모든 라우터가 이 풀을 공유하며 효율적으로 커넥션을 빌려 쓰게 됩니다. `PyMySQL`과 `DBUtils`를 조합하여 이 패턴을 구현하는 방법을 코드로 보여드릴게요.

### 1. 전역 풀 설정 및 LifeSpan 구현 (`database.py`)

앱의 수명 주기(Lifecycle)를 관리하는 `lifespan`을 사용하여 풀을 생성하고 닫습니다.

```python
import pymysql
from dbutils.pooled_db import PooledDB
from contextlib import asynccontextmanager
from fastapi import FastAPI

# 1. 전역 변수로 풀 선언
db_pool = None

@asynccontextmanager
async def lifespan(app: FastAPI):
    # [Startup] 앱이 시작될 때 풀 초기화
    global db_pool
    db_pool = PooledDB(
        creator=pymysql,
        maxconnections=10,    # 최대 연결 수
        mincached=2,         # 최소 유효 연결 수
        blocking=True,       # 풀이 가득 찼을 때 대기 여부
        host='localhost',
        user='your_user',
        password='your_password',
        database='your_db',
        cursorclass=pymysql.cursors.DictCursor
    )
    print("DB Connection Pool이 생성되었습니다.")
    
    yield  # 앱이 실행되는 동안 대기
    
    # [Shutdown] 앱이 종료될 때 풀 닫기
    db_pool.close()
    print("DB Connection Pool이 닫혔습니다.")

# 2. Dependency Injection용 함수
def get_db():
    conn = db_pool.connection()
    try:
        yield conn
    finally:
        # close()를 호출하면 연결이 끊기는 게 아니라 풀로 '반납'됩니다.
        conn.close()

```

### 2. FastAPI 앱에 적용 (`main.py`)

위에서 만든 `lifespan`을 FastAPI 인스턴스에 등록합니다.

```python
from fastapi import FastAPI
from database import lifespan
from routers import users

app = FastAPI(lifespan=lifespan)

app.include_router(users.router)

```

### 3. 라우터에서 사용 (`routers/users.py`)

```python
from pymysql.connections import Connection
from database import get_db

router = APIRouter()

@router.post("/auth/login")
```

### 4. 이 패턴의 장점

1. **자원 효율성:** 앱이 실행되는 동안 `db_pool` 하나만 존재하므로 메모리 낭비가 없습니다.
2. **테스트 용이성:** 테스트할 때 `get_db`만 가짜(Mock) DB 연결로 갈아끼우면(Dependency Override) 라우터 코드를 수정하지 않고도 테스트가 가능합니다.
3. **코드 깔끔함:** 라우터마다 `try-finally`와 `con.close()`를 복잡하게 신경 쓸 필요가 줄어듭니다. (DI가 반납까지 관리해주기 때문입니다.)

### ⚠️ 주의할 점

* **Thread Safety:** `PyMySQL`은 기본적으로 비동기(`asyncio`) 라이브러리가 아닙니다. 따라서 FastAPI 라우터 함수를 `async def`로 선언하고 내부에서 `PyMySQL`을 쓰면 성능 병목이 생길 수 있습니다.
* **해결책:** 아주 많은 요청을 처리해야 한다면 **`def login(...)`** (async 제거)으로 선언하여 FastAPI가 별도의 스레드 풀에서 실행하게 하거나, `aiomysql` 같은 비동기 드라이버를 검토해보는 것이 좋습니다.

---

### 1. 리뷰어의 지적이 중요한 이유

1. **Fail-Fast (빠른 실패):** 서버가 구동되는 즉시 에러를 발견해야 합니다. 잘못된 설정으로 서버가 어설프게 돌아가다가 나중에 DB 연결 시점에 터지면 원인을 찾기 더 힘듭니다.
2. **명확한 가이드:** `TypeError`는 개발자에게 "코드가 잘못됐나?"라는 오해를 줍니다. 반면 "MYSQL_PORT 환경 변수가 없습니다"라는 메시지는 "아, 설정 파일을 안 옮겼네!"라고 즉시 해결책을 제시합니다.
3. **애플리케이션 견고함:** 특히 `int(None)` 같은 상황은 파이썬에서 가장 흔하게 발생하는 런타임 에러 중 하나입니다.

```python
def get_env_or_raise(key: str, default=None):

db_config = {

    "user": get_env_or_raise("MYSQL_USER"),
    "password": get_env_or_raise("MYSQL_PASSWORD"),
```

FastAPI를 사용 중이시라면, 리뷰어의 기대를 200% 충족시킬 수 있는 방법이 있습니다. 바로 `pydantic-settings` 라이브러리를 사용하는 것입니다.

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):

    mysql_port: int = 3306  # 기본값
    mysql_db: str
    mysql_user: str
    mysql_password: str
    mysql_charset: str = "utf8mb4"

    class Config:
        env_file = ".env"

# 설정 로드 시 타입 체크와 누락 여부를 자동으로 검증합니다.
settings = Settings()

```

이 방식을 쓰면 리뷰어가 걱정하는 **NoneType 에러, 타입 불일치 에러**를 Pydantic이 알아서 잡아주고 예쁜 에러 메시지를 띄워줍니다.

중요한 설정값은 기본값을 주지 않고, 없으면 아예 에러를 내는 게 더 안전해요. 잘못된 설정으로 프로덕션 DB에 연결되는 것보다는 빨리 실패(fail-fast)하는 게 낫거든요.

password = os.getenv("MYSQL_PASSWORD")
if not password:
    raise ValueError("MYSQL_PASSWORD is required")
이렇게 하면 설정 누락을 바로 발견할 수 있어요. 어떻게 생각하세요?
실무에서 Fail-Fast(빨리 실패하기) 원칙을 강조하는 이유는, 어설프게 기본값으로 서버가 구동되었다가 엉뚱한 DB(로컬이나 테스트 DB)에 연결되어 데이터를 오염시키거나 삭제하는 대참사를 막기 위함입니다.

15. ALLOWED_USER_FIELDS = frozenset({'email', 'password', 'nickname', 'profile_image_url'})
화이트리스트 상수가 오염될 가능성 : 백틱(`)으로 감싸주신 건 좋은데, key 자체에 백틱이 포함되어 있으면 어떻게 될까요?

예를 들어 만약 누군가 ALLOWED_USER_FIELDS를 수정해서 email\nickname`같은 값을 넣으면 백틱 이스케이핑이 깨질 수 있어요.
화이트 리스트 상수형을 frozenset시켜 절대 수정 금지로 만들고, 주석처리하여 상수값을 개발자가 임의로 수정하지 못하게 한다.

Response body에 refresh_token을 담아서 보내고 있는데, 이거 의도하신 건가요?

Refresh token은 HttpOnly 쿠키로만 전달하는 게 안전해요. Response body에 담으면 JavaScript에서 읽을 수 있어서 XSS 공격에 취약해져요.

실무 팁:
현재 response.set_cookie()로 이미 쿠키에 담고 계시니까, response body에서는 빼는 게 좋을 것 같아요.
